## 一、初步核查（只读清点级，尚未深入）

**有，而且不是"类似"，是同一套设计思路。** s10 描述的核心特征——任务有前置依赖、有负责人、有状态、可被认领与解锁——在 Claude Code 的 2.1.88 快照里都能找到对应物：

- 面向模型存在成组的任务工具：创建 / 列举 / 查询 / 更新（对应 s10 的 create_task、list_tasks、get_task、update_task）。
- 任务结构里确实包含"前置任务列表"这一字段（s10 的 `blockedBy`），并且列举结果会把已被解决的前置项过滤掉，只显示仍未完成的前置。
- 任务有负责人字段与 `pending / in_progress / completed` 状态；新建任务默认无负责人、状态为 `pending`，需要用更新工具显式指派。
- 存在一个任务列表监视机制，会在依赖被解决时做出反应（与 s10 "完成后扫描刚被解锁的下游任务"的意图一致）。
- 同时存在旧的清单式工具（整表替换的待办清单）与新的任务工具，代码里有明确的功能开关区分两者。

以上仅用于确认"是否值得立项"，具体语义、存储位置、生命周期等机制细节尚未展开研究。

## 二、研究目标

用机制语言回答：这套任务系统解决什么问题、什么时候被创建与更新、状态如何流转、依赖如何解锁、谁来认领、数据存在哪里、跨会话（或压缩后）如何恢复、与多 agent 及后台异步执行如何衔接，以及它相对 s10 教学实现多了什么、少了什么。

## 三、研究对象

以 Claude Code 本地源码快照（`claude-code-2.1.88-source`）为主。

`learn-claude-code/s10` 只作为**参照物**用于对照（它的字段语义已知），不作为研究对象，也不会去评价它的实现质量。

## 四、需要你确认的一处范围歧义

"Task System" 在 Claude Code 里可能指向两套东西：

1. **模型维护的任务清单**：创建 / 更新 / 列举 / 查询，带依赖与负责人——与 s10 直接对应。
2. **后台任务系统**：后台命令、子代理、远程执行体、定时任务等异步运行体，以及它们的进度展示与停止控制。

**我的建议：主攻第 1 套**（与你的问题直接对应），第 2 套只在"两者如何衔接"处做必要的边界说明（例如任务清单里的条目与真正在后台执行的东西是什么关系，谁决定把某条任务变成后台运行）。如果你其实想研究第 2 套，说一声，我换范围。

## 五、拟研究内容（按建议范围）

1. **任务的数据模型**：字段、状态机、依赖的表示方式与语义（能否成环、重复添加依赖如何处理、前置任务被删除时怎么办）。
2. **创建与更新的契约**：为什么拆成两个工具；依赖为什么不能在建任务时一次性给出（s10 给的理由是：同一批并行工具调用拿不到彼此的返回值，我想确认 Claude Code 是否出于同一原因，还是另有约束）。
3. **认领与完成**：负责人由谁设置、认领的准入条件（状态 + 依赖）、完成后如何识别"刚刚被解锁"的下游任务、并发认领如何处理。
4. **存储与生命周期**：任务存在哪里（会话状态还是磁盘文件）、跨会话恢复与压缩后如何保留、多 agent / 多进程同时读写时的一致性。
5. **与主循环的耦合**：任务列表如何回到模型上下文（提醒注入的触发条件、频率与"闲置提醒"）、如何驱动界面上的进度显示、开关如何影响这些行为。
6. **边界与异常**：功能开关与灰度、失败行为、数量与长度上限、非法依赖（自依赖、环、指向已消失的任务）的处理。
7. **与 s10 的逐条对照**：语义一致的部分、更复杂的部分（例如多 agent 团队场景下的负责人语义）、以及 s10 未涉及的部分。

## 六、预期成果

一份机制层报告（正文不含源码标识符，源码依据集中在文末）。读完后应当能完整还原一次典型运行过程：

> 模型把大目标拆成若干任务 → 建立依赖关系 → 认领可开始的任务 → 完成后解锁下游 → 会话中断或压缩后仍能恢复进度 → 多 agent 场景下按负责人协作。

并附设计取舍与证据分级。

## 七、已知的不确定性与风险

- 该功能可能受开关或灰度控制，**线上默认值无法从本地源码判定**；凡涉及"生产是否默认开启"的判断，我会标注为不确定。
- 快照中同时存在新旧两套清单机制，我会说明二者的关系与迁移状态，而不是把旧机制误当成新机制的一部分。
- 如果第 1 套与第 2 套在数据层面其实是同一份结构（即"任务"同时充当执行体），我会以源码为准调整讲解结构，并在报告中说明这一发现。
