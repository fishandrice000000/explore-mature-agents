# multi-agent - Poirot - 02 - 有没有常驻型 Agent

---

没有常驻多 Agent 的形式吗?

---

## 结论

**没有。** Poirot 里不存在「常驻 Agent」这一形态：没有会被唤醒来接活、干完继续待命的队友；没有身份、邮箱、驻留槽位、恢复与打断；也没有把任务交给后台 Agent 然后继续对话的入口。

上一轮研究的委派形态（把外部 CLI 当一次性工具）与「常驻」在结构上是互斥的——Poirot 的委派被实现成**父轮次里一次阻塞的工具调用**，子 Agent 的生命周期被绑定在这次调用上：起来、干完、进程关掉。调用结束，子 Agent 就不存在了。

不过 Poirot 进程里确实有若干**常驻的东西**，容易被误认为「常驻多 Agent」。它们分四层，逐层说清。

## 一、进程层：常驻的只有 Poirot 自己

子 Agent 执行体全都是一次性的：

- **外部 CLI**：每次委派启动新进程，结束时关闭。pi 明确以「不带会话」的方式启动（不落盘会话、不复用），codex 的 ACP 会话每次新建，claude 则是一次性命令调用；
- **自拷贝副本**：虽然跑在同一个进程里，但每次委派都新建一份图与一份全新状态，跑完即弃。

因此「同时存在多个子 Agent」这件事在 Poirot 里并不成立：同一时刻最多是「一个委派正在同步执行」，加上可能同批并发的若干次调用（取决于图运行时对同步工具的调度，见第一轮笔记）。

## 二、线程层：三个常驻后台线程，都不是 Agent

这是最容易被当成「常驻 Agent」的一层。实际上这三个线程都不接任务、不做对话、不持有任务上下文：

| 常驻线程 | 干什么 | 为什么不算 Agent |
|---|---|---|
| 安装器线程 | 首次启动时后台执行依赖安装（pi CLI 的 npm 安装），完成后写标记文件 | 一次性安装动作，装完即退出；不感知任何任务 |
| 演化工作线程 | 单线程串行消费一个队列：被投递「演化任务」时，读指标 → 归因失败 → 生成候选改动 → 跑对照评测 → 决定是否晋升 | 处理的是**指标与配置产物**，不是用户任务；不产出一段对话，也不被模型调用 |
| 健康检查线程 | 周期（6 小时）扫描指标，发现指标退化就往演化队列投一个任务 | 只有一句话的工作：读指标、可能入队；其余时间在睡 |

三个线程的共同点：**被动、无任务、不产出文本、不与主模型通信**。它们是「后台指标/维护循环」，在 Agent 架构里属于可观测性与自演化基础设施，与「常驻队友」不是同一类东西。

## 三、对象层：常驻的是「接线」，不是「活着的 Agent」

进程内确实长期存活着一批对象：specialist 注册表、每个 specialist 的包装对象、它们的执行器、指标库、配置。它们从启动到退出一直在内存里。

但它们是**无状态接线**：

- 包装对象只是「名字 + 能力声明 + 一个执行器」；
- 执行器只保存命令模板、模式参数、凭证与沙箱句柄，不保存任何一次调用的进展、历史或待办；
- 注册表是只读查找表（注册后基本不再变），没有「空闲/忙碌」状态、没有队列、没有租约。

所以「常驻」的只是**能力清单**，不是「活着的 Agent」。这跟常驻队友的关键差别在于：常驻队友的核心是**跨任务存续的会话与待办**，而 Poirot 的对象层一条都不保留。

## 四、状态层：常驻的是会话，不是 Agent

唯一真正跨轮次存续的是**主会话的状态**（对话消息、观察、待办、治理标记、活动 specialist 名单与产物引用），它由一个进程内检查点存储持有，让模式切换、模型切换后对话还能接上。

注意到这里的方向是反的：Poirot 让**父会话**常驻，而子 Agent 完全无常驻——子 Agent 不写会话、不写日志、不留运行记录，也不带自己的检查点。

## 五、为什么结构上就不可能有常驻形态

这不是「没做完」，而是几个契约合起来把常驻排除掉了：

1. **委派被建模成工具调用**。工具调用的语义是「父轮次内同步取得一个结果」，返回值是一段压缩过的 JSON。任何「派出去、继续干别的、稍后回来收」的模式都需要任务标识与回收通道，而这套契约里连字段都没有。
2. **执行契约是同步的**。执行器只提供一个「传入请求、返回结果」的同步方法，没有启动/查询/等待/取消这类异步操作。因此既无法并发编排，也无法在父轮次之外维持一个运行中的子 Agent。
3. **没有会话概念**。外部执行体每次都以「新会话」启动，自拷贝副本每次重建；没有「同一个子 Agent 第二个任务」这回事。
4. **没有控制面**。代码里没有暂停、恢复、打断、中止这些动作，也没有任务编号；连「这次委派对应哪个可查的实体」都没有。（演化层有一个「阻断」概念，但那是给演化实验用的，不是 Agent 生命周期。）
5. **没有消息通道**。子 Agent 之间、子父之间，除了「工具返回值」这一条路，没有任何投递机制。
6. **叶子深度被硬性设为 1**。自拷贝被刻意剥夺委派工具，从结构上禁止「Agent 再生 Agent」的树，而常驻形态通常需要一层可扩张的池。

## 六、与之前研究的两种常驻形态对照

工作区里已有两份同类机制笔记，对照起来能看清 Poirot 的位置：

- **Claude Code**：常驻队友 + 共享任务清单 + 文件邮箱，队友可被反复唤醒、可被分派多个任务、有并发与隔离缺口；
- **Codex**：Agent 注册表 + 消息板 + 显式生命周期控制（派生、发消息、追加任务、恢复、等待、打断、关闭），把多个 Agent 当一个受管理的工作组。

Poirot 是第三种形态：**「一次调用、一生结束」的无状态委派**。它借用了别人的 Agent（各自的循环、模型、工具面），但自己不承担「管理多个活着的 Agent」这件事——没有身份、没有驻留、没有恢复、没有通信。它实现的重心在别处：装配期可用性判定、上下文两端限幅、结果压缩成结构化 JSON、失败转可读文本、以及围绕这一切的指标与演化钩子。

## 七、带来的实际边界

- **任务不能脱离父轮次存活**：父轮次结束或被打断，子进程随之终止；没有「稍后回来收结果」的能力，也没有从断点继续的入口。
- **长任务只能同步等**：界面能做的只是把这张工具卡挂久一点（默认上限 10 分钟、自拷贝 5 分钟）。
- **无法真正并行分工**：即使模型在同一批里发起多个委派，也没有配额、队列、优先级或并发上限（配置里的并发字段无人读取）。
- **无法积累「某个子 Agent 的经验」**：子 Agent 每次都是新的，跨次不携带任何记忆；唯一跨次积累的是指标库里的计数与决策日志。

## 八、若要变成常驻形态，缺的是四件东西

按依赖顺序，缺的都不是「再加一个函数」：

1. **任务实体**：委派需要一个可寻址的编号与状态（排队/运行/完成/失败），而不是一次函数返回；
2. **异步执行契约**：执行器拆成「提交 / 查询 / 取回 / 取消」，才可能在不阻塞主循环的前提下维持多个在跑的子 Agent；
3. **回收与唤醒通道**：一个供主循环取回结果的队列或事件流；没有它，异步就只是「看不见的后台」；
4. **生命周期治理**：驻留上限、空闲回收、打断与恢复、失败重试策略——这一层才是常驻形态真正的成本所在。

## 九、证据分级

**已证实（源码可直接确认）**

- 外部执行体每次委派都新起进程、结束即关；pi 以「无会话」模式启动；codex 每次新建会话；自拷贝每次重建图与全新状态。
- 代码中不存在启动/查询/等待/取消/恢复/打断等子 Agent 生命周期操作，也不存在任务编号。
- 子 Agent 与父之间只有「工具返回值」一条通道，没有消息投递、没有共享任务清单。
- 进程内的常驻线程只有三个：安装器、演化工作线程、健康检查线程；三者都不承接用户任务、不产生对话输出。
- 注册表与执行器在进程内长期存活，但不保存任何单次调用的状态或历史。
- 唯一跨轮次存续的是主会话状态（进程内检查点），子 Agent 不参与。
- 演化/评测的命令行入口是空壳（调用即抛未实现），因此也没有「在终端里查看/管理常驻 Agent」的界面。

**合理推断（结构支持，未运行验证）**

- 同一批多个委派可能被并行执行，但没有任何配额或并发上限的约束，实际并行度由底层图运行时的同步工具调度决定。
- 父轮次被用户中断时，子进程通常随调用栈退出被终止；代码里没有为「孤儿子进程」准备回收逻辑（仅有正常的结束路径）。

**无法确认（材料不足）**

- 真实 CLI 在长任务下的驻留行为（例如子进程被强制结束时的清理效果）；未安装 CLI、未运行环境。
