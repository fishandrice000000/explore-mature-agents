# multi-agent - Poirot - 03 - 只有委派层，没有团队层

---

也就是说 Poirot 的多 Agent 只停留在 subagent 这一层面，而没有 team 这样的机制?

---

## 简短回答

方向对，但要更精确一格：

**Poirot 只有「父 → 子、一次性的委派」这一层，team（工作组）层完全没有。**而这一层里，「派给自己的副本」（真正的 subagent 语义）执行链是断的，当前唯一可能跑通的是「把任务外包给别人的 Agent 产品」（外部 CLI）。

所以更准确的说法是：**Poirot 的多 Agent = 单层外包式委派，既不是自己派生副本，也不是团队。**

## 一、把「多 Agent」拆成三层，Poirot 只落在第一层

| 层级 | 形态特征 | Poirot |
|---|---|---|
| L0 单 Agent 多能力 | 一个循环里换工具、换技能、换提示词分段 | 有（技能注入、记忆召回、待办、报告等都是单 Agent 内的能力叠层） |
| L1 单层委派 | 父把一段任务交出去，子干完把结果交回，父继续；子之间互不可见 | 有（且只有这一层） |
| L2 团队/工作组 | 多个成员共存、可被反复唤醒、任务可再分配、有共享进度与通信 | 无 |

L1 内部还要再分两种语义，Poirot 两种都写了，但只有一种可能真跑：

- **外包（外部 specialist）**：子 Agent 不是 Poirot 自己的副本，而是一个独立 CLI——自带模型、自带循环、自带工具面。Poirot 只负责送目标、收文本。**这是当前唯一可能跑通的路径。**
- **自拷贝（真正的 subagent）**：在进程内新建一份隔离状态的副本，跑同一张图。设计上写了叶子角色、共享沙箱、隔离上下文，但**调用链是断的**（调用了一个不存在的方法），所以这一种实际从未跑完过。

因此在「subagent 层面」这个说法上要打个折：**结构上它把自己副本也规划进去了，但能运转的只有外包。**

## 二、team 缺的不是一个模块，而是五个要件

team 之所以是另一层，是因为它需要下面这些东西；Poirot 逐条都没有：

1. **成员身份与常驻实体**：team 的成员有身份、有忙闲、可以被同一批人反复派活。Poirot 的 specialist 只有「名字」——注册表是只读查找表，用来生成工具名和提示词，没有忙闲状态、没有租约、没有驻留。每次派活都是重新起一个进程。
2. **共享任务池 / 可再分配的任务**：team 的核心是把任务放在中间，谁空闲谁取。Poirot 的任务是**参数**：目标与成功标准被塞进一次调用，调用结束任务就消失。父的待办清单是父私有的，**委派不会写回待办**，子也不会看到待办。
3. **成员间通信**：team 有消息、邮件箱、广播、状态同步。Poirot 只有一条通道——**工具返回值**。子与子之间零通道，子对父只有「一次性结果」，父对子只有「一次性请求」。
4. **生命周期控制**：team 需要暂停、恢复、打断、关闭、重新指派。Poirot 的委派里没有任何这类动作，连任务编号都没有，所以「那个正在跑的 Agent」在系统里不是一个可寻址的东西。
5. **并发治理**：team 需要槽位、上限、优先级、去重。Poirot 没有并发控制设施，配置里那个上限字段无人读取。

这五条合起来就是「团队」的定义；少任何一条，就退化成「调用」。

## 三、三处容易被误认成 team 的地方

- **注册表**：启动时把可用 specialist 注册进一张表，看起来像「成员名册」。但它只承载「名字 → 执行器」，作用是生成工具和提示词；它不是成员管理，也没有任何运行时状态。
- **待办清单**：看起来像「共享任务板」。实际是**单个 Agent 私有的状态字段**，由模型自己写、自己催办；委派既不读它也不写它，子 Agent 拿到的是全新状态、空待办。
- **自演化层**：Poirot 有一套「根据指标自动改进派活方式」的机制（改的是送给 specialist 的上下文模板与技能注入模板），这在 team 机制里通常不存在。但它有两个限定：默认关闭；而且**模板参数在委派点上是死参数**——工具体接收了模板读取入口却从未使用，输入端转换器接收模板参数也从未使用。也就是说这项能力连「改派活方式」这条线也没有真正接上。

## 四、单层委派带来的边界（都是必然结果，不是缺陷描述）

- **没有横向协作**：两个子 Agent 不能商量、不能分工、不能互相检查；父只能串行（或无序并发）地各派一次。
- **没有任务再分配**：子干到一半发现方向错了，只能把「缺口说明」交回来，父再发一次新调用——上下文重新抽一次、进程重新起一次。
- **没有共享进度**：父看不到子在做什么，只看到最后那段被压缩到约 2000 字的结论。
- **没有角色协商**：谁适合干什么，写在系统提示词的一段静态原则里；运行时不做能力匹配、不做负载均衡、不做失败转移（失败只回一段「建议重试或自己做」）。

## 五、与已有两种形态的定位

工作区里两份笔记分别对应「队友/团队」与「工作组/消息板」：

- Claude Code：常驻队友 + 共享任务清单 + 文件邮箱 → L2 团队层；
- Codex：Agent 注册表 + 消息板 + 显式生命周期（派生/追加任务/恢复/等待/打断）→ L2 团队层（更重控制）。

Poirot 明确停在 L1：它把「多个 Agent 如何共存」这个问题整个回避掉了，只保留「一次调用换一个外部专家」这个最小可用形态。它投在别处的精力是：装配期判定谁可用、上下文两端限幅、输出压成结构化 JSON、失败转可读文本、以及围绕这些的指标与演化钩子。

## 六、证据分级

**已证实（源码可直接确认）**

- 全仓（多 Agent 与主 Agent 路径）没有团队词汇与团队设施：无成员状态、无邮箱/消息投递、无任务池、无生命周期操作、无并发槽位。
- 委派不读写父的待办清单；子 Agent 得到的是包含空待办的初始状态。
- 注册表只做「名字 → 执行器」查找，供生成工具与提示词使用；无可变运行时状态。
- 自拷贝路径调用了不存在的方法，结构上必然失败；外包路径依赖外部 CLI 是否可用。
- 委派点接收「演化后的上下文模板」入口但从不使用；输入端转换器同样接收而不使用模板参数。

**合理推断（结构支持，未运行验证）**

- 同一批多个委派可能并行，但既无配额也无并发上限，实际并行度取决于底层图运行时对同步工具的调度。
- L1 单层结构下，父若想「两阶段协作」，只能靠多轮工具调用串起来，每轮都重新付出上下文抽取与进程启动成本。

**无法确认（材料不足）**

- 外部 CLI 在真实环境下的失败率与主模型被误导后的补救行为（未安装 CLI、未联网运行）。
