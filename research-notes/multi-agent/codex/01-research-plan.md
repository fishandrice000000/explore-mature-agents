# Multi-agent - Codex - 01 - Research plan

---

Codex 在常驻队友/团队这方面, 又是怎么做的呢?
* 如何确认什么时候开启常驻队友机制
* 多 Agent 任务间分配靠什么决定
* 多 Agent 间的通信机制
* 多 Agent 间的上下文隔离
* 多 Agent 同时工作时, 并发问题怎么处理

---

## 一、初步核查（只读清点级）

Codex 这边的多 Agent 不是"顺带做的功能"，而是一套独立成层的基础设施，形态与 Claude Code 明显不同：

- **工具面更细**：至少存在派生、发输入、发消息、追加任务、恢复、等待、列举、关闭、打断这一组操作（`spawn_agent`、`send_input`、`send_message`、`followup_task`、`resume_agent`、`wait_agent`、`list_agents`、`close_agent`、`interrupt_agent`）。
- **有两个实现版本并存**：一个旧版（协作开关）和一个新版（多 Agent v2 开关），版本选择还会受模型元数据影响。
- **有独立的控制层**：派生、邮箱、投递、完成、打断、恢复、驻留、预算、根代理交接等各自成模块。
- **有四个独立 crate**：agent-identity、agent-graph-store、agent-message-board-client、agent-roles。说明"身份、关系图、消息板、角色"被当作一等公民。

也就是说，Codex 不是"把子代理当工具调用"，而是**把多个 Agent 当作一个受管理的工作组**：有身份、有关系、有邮箱、有驻留与恢复、有预算。

这套东西恰好对应你列的五个问题，但答案形态可能和 Claude Code 很不一样（Claude Code 是"共享任务清单 + 文件邮箱"，Codex 更像"代理注册表 + 消息板 + 显式生命周期控制"）。具体差异需要正式研究后才能下结论。

## 二、研究目标

用机制语言回答这五个问题：

1. 什么时候会启用多 Agent（开关、版本选择、提示词判断、会话类型限制）；
2. 工作如何在多个 Agent 之间分配（是中心指派、共享任务池、还是角色分工）；
3. Agent 之间怎么通信（消息类型、投递语义、是否阻塞、如何唤醒）；
4. 每个 Agent 看到多少上下文（继承什么、隔离什么、子代理如何构造）；
5. 同时工作时如何处理并发（生命周期、打断、等待、预算、文件/工作区冲突）。

## 四、需要你确认的三点范围

1. **两个版本怎么处理**。
   源码里同时有旧版与 v2。我的建议：**以新版为主**，旧版只说明"差异与共存方式"，避免把两套语义混在一起讲。
2. **是否包含"角色"与"消息板"**。
   我的建议：**包含**。它们正是"常驻队友/团队"区别于"一次性子代理"的地方（身份、可再联系、可按角色分工）。
3. **是否包含工作区隔离（worktree）**。
   我的建议：**只在与并发相关的一节里讲**，不展开 worktree 本身的实现。

另外默认**不包含**云端执行体与记忆机制（分别属于别的研究主题）。

## 五、拟研究内容（按你的五个问题组织）

1. **开启条件**：功能开关与版本选择链；模型元数据是否参与；什么会话类型不允许派生；提示词层面的"何时该委派"判断（软约束还是硬约束）。
2. **任务分配**：派生时任务如何传入；追加任务与发输入的区别；是否存在共享任务池/看板；角色如何影响分工；父代理与子代理的层级关系（是否允许子代理再派生）。
3. **通信**：邮箱/消息板的存储与投递语义；阻塞式等待与异步通知；消息优先级；跨代理消息与"发给用户"的区别；失败与超时。
4. **上下文隔离**：子代理从父代理继承什么（系统提示、工具、模型、沙箱、工作目录、记忆）；对话历史是复制、摘要还是从零开始；子代理的产出如何回到父代理。
5. **并发与生命周期**：派生上限与预算；驻留策略（空闲后保留还是回收）；打断、关闭、恢复的语义；多 Agent 同时写同一工作区时的处理；等待会不会阻塞父代理。
6. **设计取舍**：与 Claude Code 的"共享任务清单 + 文件邮箱"相比，Codex 这套"注册表 + 消息板 + 显式生命周期"多付了什么成本、换来了什么能力。

## 六、预期成果

一份机制层报告（正文不含源码标识符，源码依据集中文末）。读完后应当能完整还原：

> 主 Agent 判断需要并行 → 派生带角色的子 Agent → 分配任务 → 子 Agent 独立执行并回传 → 父 Agent 等待/打断/追加 → 完成后回收或驻留 → 再次派活。

并能说清每一步的触发条件、隔离边界、并发约束与失败处理。

## 七、已知不确定性与风险

- 多 Agent 的版本选择可能受远端配置与模型元数据共同影响，**线上默认走哪一版无法从仓库判定**；我会区分"结构上存在"与"实际默认启用"。
- 若发现"团队"只是"父子代理 + 消息板"的另一种叫法（而非独立概念），我会以源码为准修正讲解结构。
- 部分行为（例如何时该委派）可能只写在提示词里，属于软约束；我会明确标注。
