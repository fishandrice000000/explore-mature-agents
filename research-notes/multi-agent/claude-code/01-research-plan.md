# Multi-agent - Claude Code - 01 - Research plan

---

Claude Code 的多 Agent 协作机制是怎么做的?

---

## 一、初步核查（只读清点级）

Claude Code 里的"多 Agent"不是单一机制，至少有三层，需要先分清，否则研究会串味：

1. **一次性子代理**：主会话把一段工作委派出去，子代理在自己的循环里跑完，把结果带回。这是最基础的原语。
2. **常驻队友（团队）**：可以创建团队、派生队友、互相发消息、共享一份带负责人和依赖的任务清单，并且队友可以是"同进程内"或"独立进程"两种形态。
3. **远端/云端执行体**：把工作送到别处跑。这一类与"协作机制"关系较远。

清点已经确认存在的协作零件包括：团队创建/删除、队友派生（进程内与独立进程两种后端）、邮箱式消息、共享任务清单（负责人/认领/依赖）、队友提示词补充、权限桥接与同步、重连、布局管理，以及一个总开关（内部构建默认开；外部构建需要显式启用并受远端开关约束）。

## 二、研究目标

用机制语言回答：多个 Agent 之间**怎么被创建出来、怎么通信、怎么分工、怎么隔离、怎么结束**，以及这套设计在什么条件下才启用、代价是什么。

重点是"协作"这件事本身，而不是把每个模块单独介绍一遍。

## 三、研究对象

Claude Code 本地源码快照（`claude-code-2.1.88-source`）。

## 五、拟研究内容（按协作生命周期组织）

1. **形态与边界**：一次性子代理与常驻队友的本质差别是什么（生命周期、上下文、是否可被再次联系、是否能认领新任务）。
2. **创建与继承**：团队如何建立；队友以什么方式被派生（进程内 vs 独立进程）；派生时继承哪些东西（系统提示、可用工具、模型、权限、工作目录、记忆），哪些是刻意隔离的。
3. **通信**：消息怎么发、怎么收、什么时候被唤醒（轮询/推送）、支持哪些消息类型（任务分配、权限请求、关闭请求等）、以及广播/定向的区别。
4. **分工**：共享任务清单如何承担协作职责（负责人、认领、依赖、忙闲判定、退出时任务退回）。这部分会引用已有的任务清单研究，只讲协作相关的一面。
5. **隔离与一致性**：每个 Agent 的上下文是否独立；记忆与文件系统如何隔离；权限如何同步或桥接；并发编辑同一工作区时靠什么避免互相踩踏。
6. **生命周期与可观测性**：空闲/忙碌如何判定；前台/后台如何切换；如何优雅关闭与强制终止；异常退出、失去连接后如何恢复。
7. **成本与治理**：并发上限、模型选择、开关与灰度、以及在什么情况下这套机制根本不可用。
8. **设计取舍**：哪些复杂度是协作本身必需的，哪些属于实现选择。

## 六、预期成果

一份机制层报告（正文不含源码标识符，源码依据集中文末）。读完后应当能完整还原一次协作：

> 用户提出一个大任务 → 主 Agent 判断需要并行 → 建立团队并派生队友 → 把工作拆成任务并分配 → 队友各自执行、必要时互相通信或请求权限 → 主 Agent 汇总结果 → 队友退出、未完成任务退回。

并说清每个环节的触发条件、隔离边界与失败处理。

## 七、已知不确定性与风险

- 团队功能对**外部构建默认关闭**，需要显式启用并受远端开关约束；因此报告里的行为要区分"结构上存在"与"默认可用"。
- 进程内与独立进程两种队友形态在能力上可能有差异（例如能否重启、能否重连），我会分别说明，不把一种形态的行为套到另一种上。
- 若发现某些协作语义只靠提示词约定（例如"什么时候该委派"），我会明确标注为软约束，而不是机制强制。
