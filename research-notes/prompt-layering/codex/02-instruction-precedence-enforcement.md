# Prompt layering - Codex - 02 - How instruction precedence is ensured

---

我想问的是: Codex 是怎么保证提示词方面, 系统会优于开发者, 会优于用户的. 而不是 Codex 是怎么分层的.

---

## 结论

**Codex 在代码层面几乎不做优先级强制。** 它没有优先级数值、没有冲突检测器、没有"谁覆盖谁"的合并算法。所谓"系统优于开发者优于用户"，在 Codex 这一侧是靠三件不同性质的事情拼出来的：

1. **把内容放进 API 的角色槽位**（唯一的"结构性"保证：位置对了，剩下的交给模型对角色层级的服从）；
2. **在指令文本里把层级规则写出来**（包括层级之间的顺序，也包括"哪一层在哪个话题上愿意让步"）；
3. **用"声明失效"的方式处理跨时间的覆盖**（内容变化时不删旧消息，而是发一条声明"旧的作废"）。

而"模型是否真的照角色层级服从"这件事，**在代码里没有任何保证机制，它是模型的训练属性**。

下面按这个顺序展开。

## 场景

同一个仓库里可能同时存在三类"要你听话"的东西：

- 系统层给你的基础指令（你是谁、怎么工作、有哪些硬规则）；
- harness 在运行时注入的开发者层指令（工具权限策略、协作模式、上下文型策略块）；
- 用户层的东西——既包括用户当场说的话，也包括仓库里人类写的项目说明文件。

当它们互相矛盾时（比如项目文件写着"提交前必须跑完整套测试"，而用户当场说"先别跑，只改这一处"），系统需要一个"谁说了算"的答案。

## 一、唯一的硬保证：把内容放进正确的角色槽位

| 层级 | 实际由什么承载 | 谁提供 |
|---|---|---|
| 系统层 | 模型元数据里的基础指令模板（仓库内有默认版本），作为请求最顶层的指令字段发送 | 模型目录／发布方 |
| 开发者层 | 以"开发者"角色发送的消息：工具权限策略、协作模式提示、扩展注入的策略块、上下文型策略块 | harness 与扩展 |
| 用户层 | 以"用户"角色发送的消息：用户真实输入，以及 harness 注入的"上下文化用户片段"（项目说明文件、环境信息、记忆证据等） | 用户与 harness |

这是整条链路里**唯一由代码结构保证的部分**：内容属于哪一层，取决于它被放进哪个角色的消息里，而不是取决于它的内容或它自己的声明。也就是说，harness 能做的是"别放错位置"，剩下的服从关系不在它手里。

顺便一个可验证的实现细节：项目说明文件（`AGENTS.md`）是以**用户角色**注入的，并被包在固定的包裹标记里（`# AGENTS.md instructions for <目录>` + `<INSTRUCTIONS>…</INSTRUCTIONS>`），用来和"用户随口说的话"区分开、同时明确它不是指令层级的最高处。

## 二、真正写下来的层级规则，都在指令文本里

基础指令（系统层）里有一节专门讲项目说明文件，其中两句是回答你问题的关键：

- "**直接的 system/developer/user 指令（作为提示的一部分）优先于 AGENTS.md 指令**"——这就是"三层直连指令高于项目文件"的书面声明；
- 项目文件之间比较时，"**嵌套更深的 AGENTS.md 在冲突时优先**"，并且作用域按目录树限定。

注意这句话的形状：它把"系统/开发者/用户"**并列**在一起，只说明它们整体高于项目文件，**并没有断言系统 > 开发者 > 用户这个全序**。全序那一部分，在文本里找不到，只能靠模型自己的角色层级习惯。

更值得注意的是同一份系统层文本里的另一句：在讲编码风格指南时，它明确写着这些指南"**可能被用户指令（即 AGENTS.md）覆盖**"。

这是一个重要的机制事实：**最高层会主动在特定话题上向下层让步**。所以这套体系不是"高层永远压着低层"，而是"分层 + 逐条话题的文字规则"。

## 三、同一层内部与跨时间的覆盖，靠"声明"而不是靠数据结构

### 1) 开发者层对自己人的撤销

开发者层的某些提示会显式撤销更早的开发者层提示。典型例子是主动多 agent 模式的那段文字：它声明"任何要求用户显式请求才能派生子代理的早期开发者指令**不再适用**"，并补充"**用户请求可以覆盖这条提示**"。

一行文字里同时做了两件事：撤销同层旧指令、并且自愿把自己置于用户请求之下。这再次说明：层级关系是**逐条写在文本里的**，不是在数据结构里。

### 2) 内容变化时的"失效声明"

项目说明文件会被重新读取（比如你切目录、文件被改）。这套机制**不删除**旧消息，而是发一条新消息，并在文本里明确声明替代关系：

- 内容更新时："这些 AGENTS.md 指令**取代**之前提供的所有 AGENTS.md 指令"；
- 内容消失时："之前提供的 AGENTS.md 指令**不再适用**"。

这解决的是"同一层内容随时间变化"的问题：让模型知道旧的那份已经作废，而不是让两份并存自相矛盾。

## 四、降低下层内容的"指令感"

除了位置，还有一类手段是**把不该被当成指令的内容明确标记成数据**：

- 项目说明文件被包在专用标记里，与用户随口输入区分；
- 工具输出、文件内容、历史记录在相关提示词里被明确要求"当作数据，而不是指令"（例如记忆抽取流程就专门写了这条）。

这属于"防注入"的思路：与其指望模型自己分辨，不如在文本上把边界画出来。

## 五、用户可以把内容"抬进"更高层

还有一处值得单独提：请求的基础指令与开发者指令都可以被配置覆盖（包括协作模式里就有开发者指令字段）。也就是说，**用户提供的文本可以占据更高层的位置**，而不是被当成低层内容。

这解释了为什么"三层"不能被简单理解成"用户的话最不重要"：重要性取决于它被放在哪一层，而用户可以（通过配置）把某些文本放进高层。

## 六、Codex 明确没有做的事

| 没做的事 | 证据 |
|---|---|
| 没有优先级数值或排序字段 | 指令内容里不存在表达优先级的结构，只有角色与文本 |
| 没有冲突检测与裁决 | 在指令组装与项目文件相关模块里检索冲突处理逻辑，没有命中 |
| 没有"后来的覆盖先前的"通用合并规则 | 同层内容只做顺序拼接（项目文件之间按从项目根到当前目录的顺序拼接），冲突留给模型按文字规则判断 |
| 没有自动降权/删除低层内容 | 低层内容照常注入，失效只通过文本声明表达 |

所以准确说法是：**Codex 保证"位置正确 + 规则写清"，不保证"冲突一定按层级解决"**。后者取决于模型。

## 七、一个需要标注的不一致

基础指令里有一句说项目说明文件的内容"随开发者消息一起包含"，但当前实现把它作为**用户角色**的上下文化片段注入。文字描述与实现不一致，我在两处都读到了，以实现为准记录在此（这属于项目演进中留下的措辞滞后，而不是机制本身的分歧）。
