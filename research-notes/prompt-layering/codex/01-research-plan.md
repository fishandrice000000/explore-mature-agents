# Prompt layering - Codex - 01 - Research plan

---

Codex 的多级提示词是怎么做的? 系统-开发者-用户, 这三级提示词的优先级是不同的. Codex 是怎么确保的?

---

## 一、初步核查（只读清点级）

先给一条重要的预期修正：**这套优先级不是靠某处的一张"优先级表"实现的**。从清点结果看，Codex 至少叠加了四类互不相同的机制：

1. **角色层级本身**：请求里确实存在独立于用户消息的"开发者"层（模型被训练为对系统/开发者层的服从度高于用户层），所以最根本的"确保"其实来自 API 的角色语义。
2. **位置与顺序**：不同类型的指令块在请求中的安放位置不同，且上下文管理/压缩逻辑会对开发者层消息做特殊处理（保留、替换或裁掉），并不是简单地全部保留。
3. **指令文本内部的显式声明**：某些指令块自带覆盖声明，例如"用户请求可以覆盖此提示""之前那条要求用户显式请求的开发者指令不再适用"。也就是说，优先级有一部分是在文字里被明确写出来的。
4. **配置层的覆盖链**：基础指令与各主题指令块本身可以被配置覆盖（例如按模型、按角色、按项目文件，项目指令还有一种专门的"覆盖文件"）。

所以这个问题的答案会是"多机制叠加 + 冲突时不做运行时裁决"，但具体每一层如何工作，需要正式研究才能给准确结论。

## 二、研究目标

用机制语言回答：

- 三个层级各自承载什么内容、分别由谁提供；
- 一次模型请求是怎么把这些层组装起来的（顺序、角色、哪些块会被裁掉或重排）；
- 系统究竟用哪些手段"确保"优先级生效，以及这些手段各自能保证什么、不能保证什么；
- 层与层、以及同一层内部发生冲突时，实际会发生什么（是否有人做裁决）；
- 压缩、子代理、以及用户自定义会如何影响这套层级。

## 三、研究对象

以 Codex 本地源码快照（`/home/fishandrice/Backend/codex`）为主。

## 四、需要你确认的两点范围

1. **是否包含"项目/用户指令文件"这一层**（例如项目根目录的 `AGENTS.md` 及其覆盖文件、以及 CLI/配置级别的指令覆盖）。

## 五、拟研究内容（按机制划分）

1. **三层各自的内容来源与提供者**：内置基础指令、按主题的开发者指令块（工具权限、协作、审查等）、项目/用户指令、以及扩展机制注入的指令块。
2. **请求组装过程**：一次会话首次请求与后续请求分别装配哪些块；每块以什么角色、什么位置进入；系统提示类内容与开发者层内容的边界在哪。
3. **保证优先级的四类机制**分别展开：
   - 角色语义（API 层能保证什么、不能保证什么）；
   - 位置与顺序策略；
   - 文本内的显式覆盖声明（哪些地方写了、写了什么语义）；
   - 配置与文件的覆盖链（谁覆盖谁、覆盖的粒度）。
4. **冲突处理**：是否存在任何运行时冲突检测或裁决；如果没有，机制的实际表现是什么（包括"口头声明优先"的边界情况）。
5. **生命周期影响**：会话压缩后开发者层与基础指令是否被保留/重建；子代理会话继承哪些层、丢弃哪些层；记忆等扩展注入块属于哪一层、为什么。
6. **可自定义点**：用户在哪些层面可以覆盖或追加指令，粒度是什么，覆盖之后优先级如何变化。
7. **边界与失败**：超长指令的截断策略、指令块缺失时的降级行为、以及各层的最小保证。

## 六、预期成果

一份机制层报告（正文不含源码标识符，源码依据集中在文末）。读完后应当能：

- 说清一次请求里到底有哪几层指令、各自来自哪里；
- 说清"优先级"是被什么机制保障的，以及这种保障在什么情况下会失效；
- 在脑中还原从"会话建立 → 组装请求 → 上下文变化/压缩 → 后续请求"的完整过程；
- 评估这套分层方式的实现复杂度来自哪些机制，以及哪些部分依赖模型遵循文本规则。

## 七、已知不确定性与风险

- 线上的真实优先级最终由模型行为体现，**源码无法证明模型是否严格按角色服从**；凡涉及这一点的判断，我会标注为机制推断。
- 该主题涉及不少开关与灰度路径（配置覆盖、实验标志），我会区分"结构上必然成立"与"仅在特定开关下成立"。
- 早期的仓库文档可能与本快照不一致（此前已发现过一处），以源码为准并在报告中说明。
