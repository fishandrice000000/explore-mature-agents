# memory-system - Hermes Agent - 03 - 记忆整理：没有过期机制，只有容量压力、漂移护栏和用户的手

---

我主要关心 Hermes 的记忆系统, 在提取, 召回, 和整理这三方面是怎么做的. 提取是怎么确保提取的记忆是有效的, 应该提取的记忆呢? 召回又是怎样将有效的记忆注入进上下文的? 记忆文件过期/失效/合并/更新, 这个部分的记忆整理又是怎么做的? 分成三篇笔记, 分别研究这个机制.

---

## 一句话结论

Hermes 的内置记忆**没有时间维度**：条目里没有时间戳、没有 TTL、没有衰减、也没有任何后台自动整理进程（后台整理器只管技能，不管记忆）。所谓"整理"只发生在三个时点——**写入时**（容量硬上限 + 精确去重 + 原子批量合并）、**外部改动时**（漂移检测与拒写）、**用户显式操作时**（审批、删除编辑、清空）。过期与失效不是被系统检测出来的，而是被"容量顶到上限"逼出来的模型判断。

## 场景

两个月后，用户的偏好已经反过来了：以前"回复尽量详细"，现在"只要结论"。此时记忆里那条旧条目会怎样？

- 不会有任何机制发现它过期。它没有时间戳，没有任何东西知道它两个月没被用到过。
- 它会一直留在系统提示里，直到①模型在某次写入时因为容量不足被要求"合并或删掉重叠条目"，顺手把它改掉；或②用户自己删。
- 如果两条矛盾的条目都在，系统允许它们共存；模型下次读到两条时只能自行判断该信哪条。

这就是 Hermes 记忆整理的全貌：**淘汰由容量触发、由模型执行、由用户兜底**。

## 机制展开

### 存储形态决定了整理的可能性

记忆是两个纯文本文件：条目之间用 `§` 分隔，条目可以多行，没有 ID、没有字段、没有元数据、没有版本号。文件里的一切都是"给人看也给人改"的。这个选择带来两个后果：一看就懂、可以手工编辑、不需要 schema 迁移；但**任何基于时间或频率的整理都不可能实现**，因为没有可依据的记录。

### 闸门一：写入时的整理（主要战场）

**容量硬拒绝，而不是自动淘汰。** 每次写入前算出"加入/替换后整份文件会到多少字符"，超上限就拒绝，并把当前全量条目回传，要求模型在**同一轮里**先合并或删除再重试。上限是整份文件的字符数（默认 2200 / 1375），不是单条限制。

也就是说，Hermes 不做 LRU、不做按使用频率淘汰、不做重要性打分排序——它把"哪条该删"这个判断**完整地交给模型**，只负责告诉它"现在没地方了，这是全部条目"。

**更新用短唯一子串定位。** 修改与删除不看 ID、不要求全文，只要一段"能唯一定位某条目的短子串"。三种结果：

| 情况 | 行为 |
|---|---|
| 匹配 0 条 | 失败，回传全量条目 + "用精确文本重试" |
| 匹配多条且内容不同 | 失败，回传各匹配项预览 + "更具体一点" |
| 匹配多条但内容完全相同（历史遗留的重复） | 对第一条执行 |
| 匹配 1 条 | 执行 |

这种"子串定位"对模型很友好（不用背诵全文），代价是**同一条目里如果出现公共词就会歧义**，所以失败反馈刻意回传预览而不只是错误码。

**合并靠一次原子批量操作。** 单条 `add` 在满容量时必然失败；Hermes 的解法是把"删旧 + 缩旧 + 加新"打包成**一次调用**，并且**只对最终结果校验预算**：

- 中间过程超出上限不算错——只要最终状态不超；
- 全部操作要么都生效、要么都不生效（任何一步格式错、匹配不到、最终超限 → 整批回滚，什么都不写）；
- 批量里的 `add` 遇到完全重复会静默跳过（幂等），不让整批失败。

这条设计直接对应一个实测问题：以前模型得"先删一轮、再等结果、再加一轮"，每次都重发整个上下文，贵且慢。

**压制整理时的暴走。** 满载失败在同一轮里连续 3 次后，工具返回终止性结果，明确要求"停止重试记忆调用，先把回复给用户"。成功响应同样刻意不回显全量条目（只回用量百分比与条目数，并写"已完成，不要重复"），因为回显会诱发模型"再找点东西修"的重复调用。

**精确去重，没有近似去重。** 新增条目与已有条目**字面完全相同**才算重复；加载时对同一文件内的重复条目去重（保留首次出现）。语义重复但措辞不同的条目会一直共存——这正是容量压力最终要处理的东西。

### 闸门二：外部改动与并发（完整性护栏）

记忆文件是纯文本，用户、`patch` 工具、shell 追加、另一个会话都可能写它。Hermes 的写法是：**先证明读到的内容是自己能无损往返的，才允许覆盖**。

- **每文件独立锁文件**：读-改-写全程持排他锁（Unix `flock` / Windows 锁），锁在单独的 `.lock` 文件上，这样数据文件本身仍可被原子替换。
- **写用临时文件 + 原子改名**：读者永远看到"旧完整文件"或"新完整文件"，不会看到被截断的中间态。
- **漂移检测**：覆盖前在锁内重读，并用两条信号判断"这份文件还是不是工具写的形状"——①重新解析再序列化能否得到完全相同的字节；②是否存在单条超过整份文件上限的条目（工具自己写的条目不可能超过整份上限，出现即说明有人把自由文本塞进来了）。命中任一 → 先存一份带时间戳的 `.bak`，然后**拒绝写入**并说明怎么收拾。
- **读失败不等于空**：文件存在但读不出来（被占用、权限变化、编码损坏）→ 拒绝写入，而不是当成空文件重写。这条注解写得很直白：把读失败当空文件，等于把用户的记忆一次性抹掉。
- **编码细节**：用 `utf-8-sig` 读，剥掉 Windows 记事本加的 BOM；解码失败按"读失败"处理，绝不用有损替换。

值得注意的是，这套护栏保证的是**不丢数据**，不是**合并变更**：两个会话对同一条条目做不同修改时，后写的一方（在锁内重读之后）会看到前者结果并整体覆盖，没有行级合并语义。

### 闸门三：加载与注入时的整理

进入系统提示的那一份副本会再过一遍处理（磁盘上的原文不动）：

- 文件内重复条目去重；
- 每条做威胁模式扫描，命中即用 `[BLOCKED: 该条目含可疑模式，已从系统提示移除]` 占位符替代——同时保留磁盘原文，让用户看得见、删得掉。

这样"被污染的记忆"既进不了模型上下文，也不会被静默吞掉。

### 闸门四：用户手上的工具

| 手段 | 能做什么 |
|---|---|
| 写入审批闸门（默认关） | 打开后所有写入先进 pending 队列（落盘 JSON，跨重启可审），用户逐条批准/拒绝 |
| `/memory pending / approve <id> / reject <id> / approval on|off` | 审阅与切换闸门；没有活跃 agent 时会临时加载磁盘存储、沿用配置里的容量上限再执行 |
| 学习图（`hermes journey delete|edit`、TUI/桌面对应入口） | 按节点 id 定位到具体条目并删除或重写；技能节点是归档，记忆节点是直接改写文件 |
| `hermes memory reset --target all|memory|user` | 清空文件，需确认 |

这是"整理"链条上唯一**不依赖模型判断**的部分。

### 会话内的一致性问题

冻结快照（见第 02 篇）意味着：会话中删掉一条记忆，系统提示里那块仍然存在，直到压缩或会话恢复触发重建。重建时还有一层校验——只有当缓存提示仍包含当前的记忆块、且没有残留"已清空存储"的旧块表头时才复用缓存，否则重建——否则会出现"记忆已经删了，但提示里还挂着"的固化状态。

### 外部 provider：整理被整体外包

一旦启用外部记忆服务，合并、冲突消解、遗忘都发生在服务端，Hermes 侧只有一个镜像写入钩子。唯一的本地实现是 Holographic：

- **内容级唯一约束**去重（同内容重复插入返回既有 id）；
- **实体解析**：从条目里抽实体、归并同名实体、再关联到事实；
- **信任分**：用户可用"这条有用/没用"反馈调整，正向 +0.05、负向 −0.10（不对称，惩罚更重），有上下限；
- **检索时的时间衰减**：`0.5^(存在天数 / 半衰期)`，半衰期可配；
- **信任阈值过滤**：低于阈值的条目在检索时直接不返回（默认门槛 0.3）。

它做到了"降权与老化"，但**没有删除与合并**——过期的事实只会越来越难被检索到，不会消失。其他 provider（mem0、Honcho、Hindsight 等）的整理策略完全在服务端，仓库里只有调用代码，无法从源码判断其合并/遗忘行为。

## 条件与边界

- **不存在**：时间戳、TTL、按时间/频率的自动清理、后台记忆整理进程、语义去重、冲突检测、行级合并、记忆版本历史（只有 `.bak` 事故快照）。
- **存在但只在特定条件下**：漂移拒写（只在 `replace/remove/批量` 路径生效，`add` 因为"只追加不覆盖"而跳过漂移检查——但仍会因读失败而拒写）、审批闸门（默认关）、Holographic 的信任分与衰减（仅该 provider）。
- **整理粒度是整份文件**：任何写入都会把内存里的条目列表整体重新序列化落盘，没有单条目原地修改。
- **字符计数用字符数**，不是 token 数；同一段中文与英文占用的"预算"不同，压缩率也不同。

## 设计取舍

- **为什么不做自动过期**：能用自然语言表达"什么该被忘掉"的规则几乎不存在；误删一条真实偏好的代价远高于留一条过时偏好。Hermes 把"遗忘"交给容量压力下的模型判断，允许它解释自己删了什么（失败信息里回传全量条目就是为了这个）。
- **为什么用纯文本 + `§` 分隔**：可人读、可手改、可被 `patch` 工具处理、可纳入备份、无 schema 迁移。代价是没有任何元数据，因此无法做基于时间/频率的整理——这是同一条取舍的两面。
- **为什么拒绝而不是自动淘汰**：自动淘汰需要重要性评分，而评分本身又需要一个模型调用——这会在每次写入时增加延迟与不确定性。硬拒绝把成本推给"恰好正在思考的模型"。
- **代价**：整理完全依赖模型"愿不愿意在这一轮把旧条目改短"。如果模型倾向于不断新增短条目而不合并，记忆会长期停在接近上限的状态，条目越碎越难读。这也是为什么工具描述里明确要求用批量操作、并给出了"合并重叠条目"的措辞。

## 证据分级

- **已证实**：无时间戳/TTL/后台整理器；容量硬拒绝与最终态校验；子串定位的三种匹配结果；批量操作的全有或全无；每轮失败上限 3 次与终止性成功响应；加载时去重与占位符替换；锁文件 + 原子改名；漂移检测的两条信号与 `.bak`；读失败拒写；`utf-8-sig`；压缩时的缓存提示校验；`/memory` 与 journey 与 `memory reset` 的入口；Holographic 的信任分、衰减、唯一约束、实体解析。
- **合理推断**：`nudge_interval` 与容量上限共同决定了"典型条目数量级"（2200 字符 / 单条约 100–200 字符 ≈ 十几到二十条）；"条目越碎越难读"是从格式与上限推出的使用体验判断，源码无此陈述。
- **无法确认**：真实使用中记忆长期停在多少占用率、模型自发合并的频率；各外部 provider 的过期/合并策略（在服务端，仓库内不可见）。
