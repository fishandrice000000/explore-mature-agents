# Context compaction - Codex - 01 - Research plan

---

Codex 的上下文压缩机制又是怎么做的?

---

## 一、初步核查（只读清点级，尚未深入）

Codex 的上下文压缩不是单一路径，至少存在四种实现，需要先分清：

- **本地摘要压缩**：由 Codex 自己调用模型生成摘要，替换当前历史；
- **远端压缩**：把压缩请求交给支持该协议的模型供应商，由服务端完成压缩；
- **token 预算压缩**：不生成摘要，直接开启一个新的上下文窗口；
- **异步/后台压缩**：在达到前台限制之前提前准备压缩结果。

清点已经确认：

- 压缩入口分布在 pre-turn、mid-turn、post-turn 和手动 `/compact` 四处，不只是用户提交新消息时检查。
- 默认自动压缩阈值与模型上下文窗口相关，模型元数据里有一条“上下文窗口的 90%”作为默认上限；配置可以调低，也可以改变计数范围（完整上下文，或只计算携带窗口前缀之后的增量）。
- 压缩实现由供应商能力决定：OpenAI/Azure Responses 以及 Bedrock 走远端 V2；不支持远端协议的供应商走本地摘要。
- 本地摘要路径会重新注入初始上下文和世界状态，并在压缩前后执行 hooks；远端路径会保留一部分消息、工具输出或图片，并有自己的 token 预算和重试策略。
- token 预算压缩不调用摘要模型，但仍然走压缩生命周期、触发压缩 hooks，并发出压缩 turn item。
- 历史层有专门的压缩检查点和恢复元数据，说明压缩不仅影响内存中的消息，也影响 rollout 与 resume。
- 若干相关能力由 feature 注册表控制：token 预算、异步压缩、保留客户端工具输出等处于 under-development 且默认关闭；图片预算处于 stable 且默认开启；远端压缩 V2 的 feature 条目处于 removed 状态，但供应商能力仍在选择 V2，语义需要正式确认。

以上仅用于确认研究范围，具体请求形状、消息取舍、失败降级和默认值尚未展开。

## 二、研究目标

用机制语言回答：Codex 在什么时机判断需要压缩、如何选择本地/远端/新窗口等实现、每种实现具体丢弃或保留了哪些上下文、压缩后如何重建状态、失败时如何降级，以及默认行为在不同供应商和 feature 下有什么差异。

## 三、研究对象

以 Codex 本地源码快照（`/home/fishandrice/Backend/codex`）为主，只读静态分析，不运行构建或测试。

与已有笔记的边界：

- 不展开 Codex 的长期记忆系统；只在压缩后重新注入记忆或上下文时说明其边界。
- 不重复完整的会话持久化与 resume 机制；只研究压缩检查点、压缩后的历史替换和恢复所需的压缩元数据。
- 不把 TUI、exec、SDK 的前端差异当成压缩机制差异；它们最终汇入 core 的同一 turn/session 运行时。

## 四、需要你确认的两点范围

1. **是否覆盖全部可见压缩实现，还是只聚焦默认供应商路径。**
   我的建议：**覆盖全部可见实现**，包括本地摘要、远端 V2、token 预算新窗口、异步/后台压缩和手动压缩，并明确标注哪些是默认路径、哪些是实验或已移除的 feature。只讲默认路径会看不到 Codex 为什么需要多套实现，也无法解释供应商差异。
2. **是否在报告末尾附与 Claude Code 的对照。**
   我的建议：**本轮先只讲透 Codex**。两者在触发阈值、远端压缩和历史表示上的差异很大；如果你要系统对照，可以另起一篇 `comparison` 笔记，避免把两个项目的机制混在一起。

## 五、拟研究内容（按机制划分）

1. **触发与计量**：自动压缩阈值如何从模型上下文窗口推导；90% 默认上限与配置覆盖的关系；完整上下文与“前缀之后增量”两种计数范围；pre-turn、mid-turn、post-turn、模型降级/兼容哈希变化、硬上下文上限分别何时触发。
2. **实现选择**：供应商能力、feature 开关和模型元数据如何决定走本地摘要、远端 V2、token 预算新窗口或异步压缩；失败时是否回退到另一种实现。
3. **本地摘要压缩**：摘要提示与摘要前缀的结构；压缩请求如何构造；历史如何被替换；初始上下文、世界状态、用户目标、权限和工具状态如何重新注入；保留工具输出与图片的预算。
4. **远端压缩 V2**：请求里如何表达压缩触发；服务端返回什么；客户端保留哪些消息/工具输出/图片；保留 token 预算、流式重试和模型回退如何处理；与本地摘要的边界。
5. **token 预算压缩**：什么条件下选择它；为什么它不生成摘要；新上下文窗口如何建立；`new_context_window` 工具与自动压缩的关系；hooks 和 turn item 如何表现。
6. **压缩后状态与恢复**：压缩检查点、压缩后的 rollout 记录、窗口编号与窗口 ID、恢复时如何识别最后一次有效压缩；哪些状态是内存态，哪些需要持久化。
7. **失败与降级**：远端压缩不可用、流式失败、压缩请求超长、模型切换、压缩后仍超限、用户中断时分别怎么处理；是否存在重试上限或熔断。
8. **默认行为与 feature 边界**：默认供应商、默认配置、feature 注册表默认值叠加后，普通用户实际会看到哪条路径；哪些能力只在 under-development、内部构建或特定供应商下存在。
9. **设计取舍**：本地摘要、远端压缩、新窗口三种策略各自解决什么问题；为什么 Codex 需要 provider-specific 压缩；代价是什么（信息损失、额外请求、恢复复杂度、供应商耦合）。

## 六、预期成果

一份机制层报告（正文不含源码标识符，源码依据集中在文末）。读完后应当能完整还原一次典型压缩：

> 上下文增长 → 触发条件命中 → 按供应商能力选择压缩实现 → 摘要或新窗口替换历史 → 重新注入必要状态 → 写入压缩检查点 → 后续回合基于新窗口继续。

并附压缩实现对照表、触发条件与默认值表、失败降级路径、证据分级和源码依据。

## 七、已知不确定性与风险

- 远端压缩的服务端实现不在仓库中，只能确认客户端发送什么、如何处理响应，不能确认服务端实际如何压缩。
- feature 注册表的 `Removed`、`UnderDevelopment` 等 stage 与实际运行时默认值之间的关系需要核对；不能只凭 stage 推断线上行为。
- 模型元数据、供应商能力和部分阈值可能来自远端配置，线上默认值无法仅凭本地源码判定。
- 压缩与 resume、rollout、世界状态、工具输出保留、图片预算耦合较深，研究时需要区分“压缩时发生”与“恢复时重建”。
- 快照中有多套相似命名（compact、remote compaction、token budget、new context window），不能把不同实现的语义混在一起。
