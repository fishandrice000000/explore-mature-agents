Pi 的上下文压缩是怎么做的?

---

## 一、初步核查（只读清点级，尚未深入）

Pi 的上下文压缩至少有三条相关路径，但主次不同：

- **常规压缩**：上下文超过阈值或用户执行 `/compact` 时，把旧消息总结成结构化摘要；
- **溢出恢复**：模型报上下文溢出或截断响应后，压缩并最多重试一次；
- **分支摘要**：通过 `/tree` 切换分支时，把即将离开的分支总结后注入新分支。

清点已经确认：

- 默认配置里压缩是开启的；默认预留 16384 token 给模型输出，默认保留最近 20000 token 的消息；
- 自动压缩在工具结果追加后、下一次助手响应前检查，也会在提交新用户提示前检查；
- 压缩会写入会话树中的 `compaction` 条目，记录摘要、保留起点、压缩前 token 和摘要用量；恢复时从当前分支投影出模型实际看到的上下文；
- 默认摘要使用结构化交接格式，并跟踪读取/修改过的文件；重复压缩会把上一次摘要作为迭代上下文；
- 存在扩展钩子 `session_before_compact`，可以取消压缩或提供自定义压缩结果；
- 溢出恢复会先把失败的助手尝试标记为上下文不可见，再压缩并最多重试一次；
- `branch_summary` 与 `compaction` 共享摘要和文件跟踪机制，但触发场景不同；
- `packages/durable` 也有一套独立的压缩实现，但当前 CLI 的 `coding-agent` 不依赖它，不能混为一谈。

以上仅用于确认研究范围，具体切点规则、摘要格式、状态变化和失败路径尚未展开。

## 二、研究目标

用机制语言回答：Pi 在什么时机判断需要压缩、如何选择切点、摘要请求包含什么、压缩后模型实际看到哪些消息、失败或溢出时如何恢复、扩展如何介入，以及默认行为与各条压缩路径的边界。

## 三、研究对象

以 Pi 本地源码（`/home/fishandrice/Backend/pi`）为主，重点在 `packages/coding-agent` 的 `AgentSession`、`SessionManager` 与 `core/compaction`，只读静态分析。

与已有笔记的边界：

- 不展开 Pi 的完整会话树与分支切换机制；只在压缩条目、分支摘要和恢复投影处说明。
- 不研究 `pi-durable` 的独立压缩实现；它不属于当前 CLI 的会话路径。
- 不逐条枚举所有内置扩展；只说明压缩扩展钩子的接口和默认路径。

## 四、需要你确认的两点范围

1. **是否把分支摘要（`/tree` 切换分支时的总结）纳入主报告。**
   我的建议：**纳入一节边界说明**。它和常规压缩共享摘要格式与文件跟踪，但不是同一个触发场景；完全不提会漏掉 Pi 的“上下文管理”另一半，展开太多又会偏离“压缩”主题。
2. **是否包含 `pi-durable` 的独立压缩实现。**
   我的建议：**不包含**。`coding-agent` 当前不依赖 `durable`，两者是不同运行时；如果以后要研究持久化运行时，可以另起主题。

## 五、拟研究内容（按机制划分）

1. **触发与阈值**：默认预留 token、保留 token、模型窗口如何决定阈值；工具批次结束后、提交新提示前、溢出/截断后分别何时检查；手动 `/compact` 与自动压缩的差别。
2. **切点与待总结范围**：如何从会话树投影中向前累积 token；如何在用户消息边界切分；单条用户消息跨度过大时如何在助手消息处切分；为什么不能在工具结果处切分；重复压缩如何从上次保留边界继续。
3. **摘要生成**：摘要提示的结构化字段、上一份摘要如何作为迭代上下文、文件操作如何累积、摘要请求是否写提示缓存、模型/思考级别如何选择。
4. **压缩后的上下文重建**：`compaction` 条目如何被投影成模型可见的摘要消息；保留消息从哪里开始；系统提示、工具和扩展注入如何重新拼装；token 统计如何更新。
5. **溢出与失败恢复**：上下文溢出和截断响应的识别；失败尝试如何被标记为上下文不可见；压缩成功/失败/取消后是否重试、是否保留完成回答；队列和 turn 生命周期如何衔接。
6. **扩展介入**：`session_before_compact` 的输入输出；取消、替换摘要、`fromHook`、自定义 `details` 的语义；扩展摘要如何影响文件跟踪和后续压缩。
7. **默认行为与功能边界**：默认开启哪些路径、哪些设置可覆盖、哪些行为依赖扩展或 provider；自动压缩失败时用户看到什么。
8. **设计取舍**：树形会话 + 切点 + 摘要条目相对于“重写消息数组”的好处与代价；为什么保留最近消息而不是全部摘要；为什么溢出恢复只重试一次。

## 六、预期成果

一份机制层报告（正文不含源码标识符，源码依据集中在文末）。读完后应当能完整还原一次压缩：

> 上下文增长 → 工具批次结束/提交新提示时检查 → 达到阈值 → 选择切点 → 生成结构化摘要 → 写入压缩条目 → 从切点重建模型上下文 → 继续或重试。

并附触发条件与默认值表、切点规则、失败恢复路径、证据分级和源码依据。

## 七、已知不确定性与风险

- 压缩的 token 估算同时依赖 provider usage 与本地估算；不同模型、不同 provider 的实际数值可能不同。
- 默认行为可能被扩展钩子替换或取消；源码中的默认路径不等于装了扩展后的行为。
- 分支摘要与常规压缩共享部分实现，但触发和持久化语义不同，不能合并成一套结论。
- 相关测试较多，能补充边界行为；但工作区规则要求只读，不运行会写缓存或构建产物的命令。
- `pi-durable` 有同名能力，研究时必须先确认代码路径属于 `coding-agent` 还是 `durable`。
