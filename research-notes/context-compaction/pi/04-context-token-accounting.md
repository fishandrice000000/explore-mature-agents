# Context compaction - Pi - 04 - 上下文 Token 的统计方式

---

Pi 是如何统计当前上下文的 Token 数的?

---

## 结论先行

Pi 不做真实分词，也没有内置 tokenizer。它用一套**混合口径**：

1. **主口径**：取最近一次有效助手响应里供应商回报的 usage 总量，作为“截至那一刻的上下文大小”；
2. **补齐**：这次响应之后新增的消息（工具结果、新用户消息等），逐条按“字符数 ÷ 4，向上取整”估算后累加；
3. **失效回退**：如果之后发生过压缩或上下文编辑，旧 usage 不再代表当前内容，就改为对重建后的完整投影做全量字符估算。

所以“当前上下文 token 数”通常是**一个精确的历史锚点 + 一小段粗略估算**，而不是每次都把整段对话重新数一遍。所有使用方（是否压缩、`/session` 百分比、压缩前后大小）最终都落到同一个数上。

## 场景

一个长会话里，模型刚回复完，Pi 要马上回答三个问题：这轮结束后离压缩线还有多远、要不要在下一轮前压缩、界面上该显示百分之多少。三个问题都需要“当前上下文有多大”，但每次重新 tokenize 整段对话代价太高，于是 Pi 把供应商已经算好的 usage 当作锚点，只对锚点之后的增量做廉价估算。

## 机制展开

### 1. 锚点：最近一次有效响应的 usage

每次模型响应都带回一份 usage，包含四个分量和一个总量：

| 字段 | 含义 |
|---|---|
| input | 本次请求中未命中缓存的输入 token |
| cacheRead | 命中提示缓存的输入 token |
| cacheWrite | 写入提示缓存的输入 token |
| output | 本次生成的 token（含思考） |
| totalTokens | 供应商给的总量，或由前四项相加得到 |

Pi 取总量时优先用 `totalTokens`，没有才把四个分量相加。这个数之所以能当“上下文大小”：

- 输入部分覆盖了真正发出去的全部内容——系统提示、工具声明、历史消息、缓存读写都算在里面；
- 输出部分虽然还没进入下一轮输入，但下一轮它就会变成历史，所以“响应结束时的总量”正好近似下一轮请求的占用。

不同供应商的口径并不一致：Anthropic 不返回总量，Pi 自己把“非缓存输入 + 缓存读 + 缓存写 + 输出”相加；OpenAI 兼容接口先把缓存 token 从 prompt 里减出来，再四项相加；有的供应商直接透传自己的 `total_tokens`。Pi 的原则是**信任供应商给的量级，不在客户端重新定义语义**，否则缓存 token 会被算两遍或漏算。

“有效响应”有明确过滤：已中止（aborted）、报错（error）、总量为 0 的响应都不算锚点。原因是这些响应的 usage 可能只写了一半——例如流刚建立就失败，只拿到了输入侧的数字。

### 2. 增量：逐条消息的字符估算

锚点之后的消息没有 usage，只能估。规则统一而粗糙：

> 一条消息的 token ≈ 该消息所有可见字符数 ÷ 4，向上取整。

不同类型消息计哪些字符：

| 消息类型 | 计入内容 |
|---|---|
| 用户 / 工具结果 / 自定义消息 | 文本字符；图片按固定 4800 字符折算（约 1200 token） |
| 助手消息 | 文本 + 思考文本 + 每个工具调用的工具名与参数 JSON |
| Bash 执行消息 | 命令文本 + 输出文本 |
| 分支摘要 / 压缩摘要 | 摘要正文 |
| 系统消息 | 见下一节 |

图片不看尺寸也不看内容，统一按 4800 字符近似；这是整条链路里最粗的一处近似。

系统消息需要单独处理：会话树里可能存在多条系统消息（提示词补丁、工具增删），Pi 会把它们**重放合并成一条当前系统提示**——正文按顺序拼接，命名分段按名字覆盖，工具声明按增删合并——然后只计一次。工具声明（名称、描述、参数 schema）也在这一步按 JSON 字符计入，所以估算口径并没有漏掉工具定义。如果不做这个合并，历史系统消息会被重复计算，估算值会随会话变长而虚高。

### 3. 什么时候不信锚点

usage 是一个**时间点快照**。压缩和上下文编辑都会改变真正发给模型的内容，而 usage 记录的仍是旧内容。Pi 的处理是：

- 找到 usage 所属的那条会话条目；
- 找到最近一次压缩或上下文编辑条目；
- 如果 usage 所属条目更早，说明它已经过期，放弃锚点，改为对当前投影做全量估算（当前系统提示计一次 + 其他消息逐条估算）。

`/session` 和页脚更保守：如果最近一次压缩之后还没有任何有效助手响应，它们直接显示“未知”，而不是拿压缩前的 usage 冒充。因为此时任何数字都只是猜测，显示出来反而误导。

### 4. 不同用途下的取数路径

同一条“当前上下文”，在不同检查点取数方式略有差别：

| 用途 | 取数方式 |
|---|---|
| 回合结束后的自动压缩判断 | 正常响应直接用 usage 总量；存在上下文编辑时用投影估算；响应报错或 usage 为零时退化为估算，并拒绝复用压缩前的陈旧 usage |
| 新一轮请求前 / 下一次助手响应前 | 一律用当前投影估算，因为要判断的是“即将发出去的内容”，而不是上一次响应的历史快照 |
| `/session` 与页脚百分比 | 投影估算；最近一次压缩后没有有效响应时显示未知 |
| 压缩记录的“压缩前大小” | 压缩前对投影估算一次 |
| 压缩记录的“压缩后大小” | 压缩完成、重建投影后再全量估算一次 |

注意“会话累计 token 用量”（计费统计）和“上下文占用”是两个数：前者把所有历史响应和摘要调用的 usage 累加，后者只关心当前投影。

### 5. 一个直观例子

假设一条用户消息 4000 字符、模型回了一段 8000 字符的文本并调用了一次工具（参数 JSON 2000 字符），随后一个工具结果 12000 字符：

- 锚点之前的部分用供应商 usage；
- 锚点之后：助手消息约 (8000 + 2000) ÷ 4 = 2500 token，工具结果 12000 ÷ 4 = 3000 token；
- 当前上下文 ≈ 锚点总量 + 5500。

图片无论大小都按 1200 token 计，这一点和真实视觉编码差距可能很大。

## 条件与边界

- **字符/4 只是启发式**：对英文散文大致接近；对代码和 JSON（符号密集）可能偏高估，对中文、日文等表意文字会明显低估——一个汉字往往就接近一个 token，而这里只算 0.25 个。这意味着中文长会话的估算值可能远低于真实占用，实际触发点会比数字显示的更晚，最终由供应商的溢出报错兜底。
- **注释声称“保守地高估”**：源码注释把 chars/4 描述为偏保守的高估。这在英文/结构化文本上大致成立，但如上所述对 CJK 不成立，属于实现里没有覆盖到的角落（推断）。
- **usage 缺失场景**：第三方转发、部分兼容接口、流式响应中途断开，可能只带回部分分量甚至全零。这时数字会退化为纯字符估算，精度进一步下降。
- **缓存 token 是上下文的一部分**：命中缓存的输入同样占用窗口，所以相加时必须包含 cacheRead / cacheWrite；只加未缓存输入会低估。
- **输出计入上下文**：usage 总量含本次输出，这是有意的，因为它下一轮就变成历史。
- **中止响应**：后置压缩检查会跳过已中止响应；但“提交新提示前”的检查允许使用中止响应的 usage，因为流开始时拿到的输入侧数字仍有参考价值。
- **模型窗口的来源**：显示和阈值判断使用当前实际路由到的物理模型的窗口；虚拟模型或切换模型时，用的是真正执行请求的那个模型的限制。
- **工具声明的覆盖**：估算路径依赖系统消息里的工具声明集合。如果某扩展把工具定义放到别处而不经过系统消息重放，估算就会漏算这部分（推断）。

## 设计取舍

- **不引入 tokenizer**：Pi 支持几十家供应商和大量本地模型，各家分词器不同；引入精确分词既要维护依赖，又要在每次渲染、每次判断时跑一遍长文本。用供应商回报的 usage 既免费又精确，是明显的性价比选择。
- **锚点 + 增量，而不是纯估算**：纯估算在长会话里误差会累积；纯 usage 又无法覆盖锚点之后的新消息。混合方式把误差限制在“最近一批消息”内。
- **宁可提前压缩**：字符估算与向上取整在英文场景偏保守，少一次撞上供应商硬上限的风险；代价是可能多做一次摘要调用。
- **过期 usage 一律作废**：压缩后立刻用旧 usage 判断，会导致“刚压缩完又触发压缩”的死循环。失效检测和“压缩后显示未知”都是为这个边界服务的。

## 证据分级

- **已证实**：锚点取最近一次有效助手 usage、`totalTokens` 优先与四分量兜底、中止/报错/零值过滤、chars/4 向上取整、图片 4800 字符、各消息类型的计入字段、系统消息重放合并后只计一次、压缩/编辑后的失效判定与全量回退、各检查点的取数路径、压缩后无有效响应时显示未知。
- **合理推断**：中文等表意文字被显著低估；估算路径对非标准工具声明来源的漏算风险；注释“保守高估”的实际方向。
- **无法确认**：具体供应商或转发服务返回的 usage 是否精确、是否包含思考 token 的全部口径——这些取决于各家 API，仓库只能被动接受。
