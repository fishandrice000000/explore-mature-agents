# Context compaction - Claude Code - 01 - Research plan

---

Claude Code 是怎么做上下文压缩的?

---

## 一、初步核查（只读清点级，尚未深入）

压缩不是单一动作，而是嵌在主查询循环里的一条分层流水线。清点已经确认：

- 在调用模型前，主循环会依次执行历史剪裁、微压缩、自动压缩等步骤，它们各自处理不同粒度的上下文，并非互斥的替代方案。
- 压缩服务目录里同时存在：整段摘要压缩、自动压缩的阈值判断、微压缩、基于 API 上下文编辑的微压缩、会话记忆压缩、摘要提示词、消息分组、压缩后清理与警告状态。
- 手动 `/compact` 有独立命令入口，与自动压缩共用底层摘要流程，但可以带自定义指令，并可能支持按方向保留部分历史。
- 部分压缩分支由构建期开关控制，其实现文件不在本快照中（例如响应式压缩、历史剪裁、上下文折叠），目前只能确认调用点与设计意图，不能确认内部算法。
- 已有会话历史笔记讨论过压缩边界在 JSONL 和 `/resume` 中的表现，但没有展开压缩本身如何触发、如何生成摘要、压缩后如何重建上下文。

以上仅用于确认研究范围，具体阈值、消息取舍和状态变化尚未展开。

## 二、研究目标

用机制语言回答：Claude Code 在什么时机压缩上下文、有哪些不同层次的压缩、每一层具体丢弃或改写了什么、压缩后的上下文如何重建、失败时如何降级，以及这套多层设计解决了什么问题、付出了什么代价。

## 三、研究对象

以 Claude Code 2.1.88 本地源码快照（`claude-code-2.1.88-source`）为主，只读静态分析。

与已有笔记的边界：

- `session-history/claude-code` 负责会话持久化与恢复；本主题只说明压缩边界如何写入会话记录、压缩后哪些状态需要重建，不重复恢复主链的完整机制。
- `memory-system/claude-code` 负责长期记忆；本主题只在“会话记忆压缩”作为一种压缩变体时涉及，不展开记忆的生成、整理与召回。

## 四、需要你确认的两点范围

1. **是否覆盖全部可见压缩层次，还是只聚焦整段摘要。**
   我的建议：**覆盖全部可见层次**，包括自动压缩、手动压缩、微压缩、会话记忆压缩，以及历史剪裁和响应式压缩的调用点说明。只讲整段摘要会看不出“为什么要分层”，也无法解释压缩失败或压缩后仍然超长时系统怎么处理。
2. **快照中缺失的 feature-gated 实现如何处理。**
   我的建议：**按“调用点可证实、内部算法无法确认”记录**，不尝试从其他版本或公开资料补全。报告会明确区分“结构上存在这条路径”和“这条路径具体怎么做”。

## 五、拟研究内容（按机制划分）

1. **触发与计量**：上下文长度如何统计与估算；自动压缩的阈值、余量、警告线与检查时机；哪些配置和开关会改变行为；手动触发与自动触发的差别。
2. **压缩前的分层处理**：微压缩如何选择可丢弃的工具结果；如何与提示缓存、API 上下文编辑配合；历史剪裁和上下文折叠在流水线中的位置；各层为什么按这个顺序执行。
3. **整段压缩**：摘要请求如何构造、使用什么提示结构、是否流式、如何指定保留重点；手动 `/compact` 的自定义指令与部分压缩方向分别意味着什么。
4. **压缩后的上下文重建**：摘要消息、压缩边界标记、最近读取文件、计划、技能、增量附件、已读状态和 token 统计如何重新注入；哪些信息被永久丢弃，哪些只是换了表示形式。
5. **失败与边界**：压缩调用失败、没有摘要文本、网络中断时如何处理；上下文仍然超长时的响应式路径；如何防止连续重复压缩；压缩后 token 仍高于阈值时会发生什么。
6. **状态与持久化**：压缩期间写入会话文件的元数据、压缩边界的语义、UI 进度与警告提示；压缩如何影响后续自动压缩判断和会话恢复。
7. **设计取舍**：摘要压缩、微压缩、历史剪裁各自解决什么问题；为什么需要多层组合；代价是什么（信息损失、额外模型调用、缓存失效、延迟）。

## 六、预期成果

一份机制层报告（正文不含源码标识符，源码依据集中在文末）。读完后应当能完整还原一次压缩过程：

> 上下文逐步增长 → 先清理低价值工具结果 → 接近阈值时触发摘要 → 生成摘要并写入边界 → 重建必要的文件与状态附件 → 后续回合基于压缩后的上下文继续。

并附压缩层次对照表、关键条件与数值、失败降级路径、设计取舍和证据分级。

## 七、已知不确定性与风险

- 多个压缩分支受构建期或远端开关控制，**线上默认启用哪条路径无法仅凭本地源码判定**；报告会区分“代码结构上存在”与“生产默认生效”。
- 快照缺少部分 feature-gated 实现文件，这些分支只能讲到调用点和预期职责，不能给出内部算法。
- 自动压缩阈值可能依赖模型、配置和运行时估算方式，源码中的常量不一定等于用户实际看到的触发点。
- API 侧上下文编辑和提示缓存的实际行为有一部分在服务端，源码只能证明客户端如何请求，不能证明服务端如何执行。
