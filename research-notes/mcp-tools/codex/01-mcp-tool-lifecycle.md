# MCP 工具接入 - Codex - 01 - 作为 MCP 客户端的工具发现、暴露与调用

---

我想探究一下 Claude Code / Codex 作为 MCP 客户端，如何发现外部 MCP Server 提供的工具，把工具暴露给模型，并在模型请求调用后完成权限判断、协议调用、结果转换与失败处理。

---

本文只讨论 Codex 作为 MCP 客户端的工具链路，不讨论 MCP resources、prompts，也不讨论 Codex 自己作为 MCP Server 对外提供工具的实现。

## 结论摘要

Codex 把 MCP 工具纳入 core 的统一工具路由，但它比“取回工具列表然后直接注册”多了一层目录快照。每个 Server 先独立启动、初始化、分页发现工具并形成当前目录；连接管理器再把所有 Server 的目录汇总、过滤、规范化并发布为一个绑定。模型请求使用这份冻结的目录生成工具声明，真正调用时又绑定到同一份目录快照和对应客户端。

暴露方式取决于模型能力。模型支持工具搜索时，MCP 工具默认进入延迟目录，模型通过 `tool_search` 用关键词查找并加载 schema；不支持搜索时，工具直接进入模型工具列表。Code Mode 开启时，同一工具还可能通过代码执行入口暴露。Server 配置、应用策略和“从某些表面隐藏”的设置可以进一步限制可见范围。

权限不是只看 MCP 的危险标记，还叠加 Server 或单工具的审批模式、全局审批策略、自动审查、hooks 和记忆授权。调用成功后，Codex 保留 MCP 的内容、结构化结果、错误标记和元数据，再把结果转成模型输入；过大的结果按模型或单工具预算截断。

## 机制展开

```mermaid
flowchart LR
  A[配置、插件与扩展贡献 Server] --> B[按 Server 建立连接]
  B --> C[初始化与能力协商]
  C --> D[分页发现工具]
  D --> E[目录过滤、命名和 schema 适配]
  E --> F[发布不可变工具绑定]
  F --> G{模型支持搜索?}
  G -->|是| H[延迟目录与工具搜索]
  G -->|否| I[直接工具声明]
  H --> J[模型请求工具]
  I --> J
  J --> K[目录绑定与审批]
  K --> L[MCP 协议调用]
  L --> M[结果处理与预算控制]
  M --> N[工具结果回到模型]
```

### 1. 配置先变成运行时 Server 目录

Codex 的 MCP Server 可以来自用户配置、项目配置、插件、扩展贡献以及内置的 Codex Apps 连接。运行时会把配置层级、插件选择、当前线程、认证状态和执行环境投影成一份当前有效的 Server 目录；不同线程或不同执行环境可以有不同视图。

每个 Server 可以启用、禁用或标记为必需。配置还能控制：

- 启动超时与工具调用超时。
- 工具白名单、黑名单。
- Server 默认审批模式与单工具覆盖。
- 输入 schema 压缩预算与单工具输出 token 预算。
- 是否从直接模型面、延迟搜索面或 Code Mode 面隐藏。
- 是否要求只读工具。

配置解析和执行权限绑定在同一个快照上。调用开始后，即使用户配置发生变化，已经准备的调用仍保留当时的权限 profile，避免“审批时看的是一个 Server，执行时换成了另一个配置”。

### 2. 建立连接并形成单个 Server 的目录

连接管理器为每个启用的 Server 维护独立客户端和状态。配置未变化且旧客户端仍可用时，会复用已有连接；认证、环境、传输或目录输入变化时，则替换客户端。

启动流程是：

1. 建立本地进程或远程传输。
2. 完成 MCP 初始化握手，声明客户端能力，取得 Server 能力和协议版本。
3. 如 Server 明确禁用目录缓存，关闭该 Server 的目录缓存。
4. 请求并汇总所有工具页。
5. 生成不可变的客户端工具目录，同时记录工具、Server 信息与刷新版本。

普通 Server 默认启动超时约 30 秒，默认单次工具调用超时约 300 秒；配置可以覆盖，调用方也能给出更短的预算，最终取两者较小值。

工具发现会完整消费分页：

- 最多 100 页。
- 普通 Server 最多 2,048 个工具，受信任的 Codex Apps 目录最多 8,192 个。
- 单个 cursor 最多 64 KiB。
- 重复 cursor、超页数、超总数或整体超时都会让本次目录发现失败。

远程 `tools/list` 的瞬时传输错误有有限重试；会话过期的 404 会触发重新初始化并重试。某个可选 Server 发现失败时，其他 Server 仍能形成目录，模型请求可以在可用工具中继续。

### 3. 目录先经过可见性与策略过滤

对于普通 MCP 工具，原始 Server 名和工具名被保留用于协议调用；模型侧另有规范化名称。默认会加上历史前缀，形成类似：

```text
mcp__<Server 名>__<工具名>
```

配置可以关闭这个前缀，也可以指定哪些 Server 不加前缀。名称会移除 API 不接受的字符，并处理重复项：

- 同一原始工具重复声明时只保留一个。
- 不同 Server 规范化后撞名时，加短哈希后缀。
- 工具名和命名空间过长时截断并用哈希恢复唯一性。
- 模型可见合并名最多 128 字节。
- 最终按原始身份稳定排序，避免目录顺序无意义抖动。

在进入模型目录之前，Codex 还会执行多层过滤：

1. Server 的启用状态和白名单、黑名单。
2. 工具扩展元数据中的 UI 可见性；没有该字段时默认可见，有该字段但未声明模型可见时隐藏。
3. Codex Apps 的 connector 与工具策略。
4. 插件归属和工具预算。

因此，“Server 返回了工具”不表示模型一定能看到；目录、visibility、策略和上下文暴露面都要同时允许。

### 4. 把工具定义适配成模型可调用的 namespace 工具

Codex 将单个 MCP 工具放入以 Server 或 connector 命名的 namespace。工具输入 schema 会先做兼容化处理：

- 缺少 `properties` 时补空对象，满足模型 API 要求。
- 清理模型不支持的 schema 形态。
- 删除不可达定义。
- 默认超过 5,000 字节时进行渐进压缩，可能移除说明、定义表和较深结构，但尽量保留顶层参数面。
- 单 Server 可以配置不同预算。

输出 schema 也会作为工具定义的一部分传给模型。Server 的说明作为 namespace 描述，说明长度有上限；插件提供的工具会增加插件来源说明。

模型看到的是过滤和压缩后的函数签名，协议调用仍使用原始工具名。执行前的 MCP 路径只检查参数 JSON 能否解析为对象，没有再次按远端 JSON Schema 做本地严格校验；参数语义由 Server 最终校验。

### 5. 决定直接暴露还是延迟搜索

当模型支持工具搜索时，普通 MCP 工具默认注册为延迟工具；模型不支持时，则默认直接暴露完整定义。之后还有三类覆盖：

- Server 或 connector 可以声明从某个暴露面省略工具。
- 配置可以把某个 namespace 指定为只直接暴露，阻止进入延迟目录。
- Code Mode 模式可以改写哪些工具通过代码执行入口可用。

延迟目录不会把所有 MCP schema 常驻在模型请求中。Codex 提供一个 `tool_search` 工具，其说明包含当前可搜索来源；搜索使用工具名、说明、namespace、Server、插件、参数名等文本建立 BM25 索引。返回结果是可加载的工具定义，模型在后续请求中才拿到对应 schema。

只有当至少有一个延迟工具可搜索时，`tool_search` 才进入模型面；没有延迟工具时不会为了空目录继续宣传搜索入口。这个设计与 Claude Code 的工具搜索逻辑方向相同，但 Codex 把搜索实现放在 core 的延迟工具目录上，并对搜索结果做了统一的 schema 归一化。

### 6. 模型调用被解析为统一工具路由

模型返回的函数调用会先转换为 Codex 内部的“命名空间 + 工具名”调用。工具路由按这个标准身份找到已注册的执行器，不依赖模型发出的扁平字符串去临时猜 Server。

调用 MCP 工具时，执行器会重新准备当前绑定：

1. 必要时刷新已经变脏的 MCP 运行时。
2. 在最新绑定中查找同名工具。
3. 找到后取得与该工具绑定的客户端、目录版本、Server 元数据、超时和权限 profile。
4. 若目录已经变化或工具不再允许，则拒绝调用，而不是把调用发给一个可能错误的客户端。

工具执行前还会运行通用 PreToolUse hooks。hook 可以阻止调用或改写参数。之后才进入 MCP 专用审批与调用阶段。

### 7. 审批由配置模式与 Server 注解共同决定

Codex 的 MCP 工具审批模式默认为 `auto`，并可在 Server 级设置默认值、在单工具级覆盖。四种模式的行为是：

- `auto`：根据 Server 注解判断。
- `prompt`：每次都需要审批。
- `writes`：只读工具可不问，其他工具需要审批。
- `approve`：该层策略不要求审批。

`auto` 对注解的处理是保守的：

- `destructiveHint = true`：需要审批。
- `readOnlyHint = true` 且没有破坏性提示：不需要审批。
- 未声明只读：若破坏性或开放世界提示为真则审批。
- 两个提示都缺失：按需要审批处理。

在这之上还有全局审批策略和自动审查。如果配置、权限 profile 或自动审查已经判定可以自动批准，MCP 专用审批会被跳过；若审批策略为 `never` 但当前调用仍需要用户批准，则直接拒绝。

用户批准可以只作用于本次、当前会话，或者写入配置使下次不再询问。可记忆授权的 key 包含 Server、插件、connector、link 与工具等身份字段，避免把 A 工具的批准错误套到 B 工具。当前代码只为 `auto` 模式建立会话级和持久级记忆；`prompt` 和 `writes` 的选择会被归一到单次批准。选中插件的 Server 不允许持久化批准。

审批界面有两种传输形态：启用相关 feature 时通过 MCP elicitation 请求客户端 UI；否则通过普通用户输入请求。非根代理线程不能直接使用普通用户输入路径，需要由父线程处理。

### 8. 调用时使用目录快照和精确客户端

审批通过后，调用会进入一个受目录快照保护的执行区：

1. 重新确认触发表单仍对应这份目录版本。
2. 处理需要改成宿主可访问路径的文件参数。
3. 构造调用元数据，包括调用 ID、线程与会话身份、来源窗口、插件、connector、沙箱状态等。
4. 应用 Server 要求的只读请求元数据。
5. 通过该工具绑定的 MCP 客户端发送 `tools/call`。
6. 在 Server 超时与调用方给出的更短超时之间取最小值。

这个“目录快照 + 精确客户端”约束解决了一个常见竞态：模型看到工具 A 时连接属于旧 Server，真正执行前 Server 配置或认证已经变化。Codex 不允许调用悄悄落到新连接上；目录变化会使旧调用准备失效。

### 9. 结果转换与预算控制

MCP 返回的内容、结构化内容、`isError` 和 `_meta` 会先转换成 Codex 协议结果。扩展生命周期可以修改工具结果，然后才转成模型输入。

转换规则包括：

- 文本变成模型输入文本。
- 图片转为内联 data URL；模型不接受图片时替换成说明文本。
- 音频转为内联音频；模型不接受音频时替换成说明文本。
- 未知内容类型序列化为文本保留。
- 存在结构化结果时，模型输入优先使用结构化结果的 JSON 文本。
- 成功与否由 MCP 的错误标记保留。

模型侧还会加入实际耗时头，再按模型默认截断策略或单工具 `output_token_limit` 截断。文本预算约留 20% 给序列化与管理开销；图片和音频按各自成本处理。事件与 UI 展示还有独立的字节上限，避免把大结果完整复制到事件流。

### 10. 失败与动态变化

主要失败路径如下：

- 参数不是合法 JSON：直接生成失败工具结果。
- 工具已从目录或权限范围移除：返回“工具当前不可用”的失败结果。
- Server 返回 `isError`：保留内容并标记失败。
- 传输错误、超时或协议错误：转换为带上下文的错误文本，再成为失败工具结果。
- OAuth 失效：返回认证所需结果和标准认证提示，不把底层 token 细节暴露给模型。
- 会话 404：重新初始化客户端并重试一次。

取消通过工具调用 token 和任务取消传播。审批等待可以被取消；工具执行任务被中断时，dispatch future 会停止。协议层是否额外向 Server 发送 `notifications/cancelled` 取决于底层 RMCP 请求对象的取消实现，当前 core 的确定行为是停止本地执行并完成终止记账。

普通 MCP Server 的 `tools/list_changed` 通知目前只写日志，**没有像 Claude Code 那样直接触发工具目录重新拉取**。[已证实] 新的目录通常要等运行时因配置、认证、插件或会话状态变化而重新发布，或者 Server 重连后再形成。Codex Apps 有自己的工具缓存与刷新路径，不应把普通 Server 的行为等同于内置 Apps。

## 条件与边界

- **已证实**：工具发现完整消费分页，并有明确的页数、条目数、cursor 长度和超时上限。
- **已证实**：模型可见名称经过规范化、冲突哈希、长度控制与稳定排序。
- **已证实**：工具先经过 Server 过滤、UI 可见性、Apps 策略和插件预算，再进入模型目录。
- **已证实**：支持工具搜索时 MCP 工具默认延迟，不支持时默认直接暴露；配置和 namespace 可以改写暴露面。
- **已证实**：调用绑定目录快照、精确客户端、Server 元数据和权限 profile。
- **已证实**：审批判断同时使用配置模式、Server 注解、全局审批、自动审查与 hooks。
- **已证实**：普通 Server 的工具清单变化通知只写日志，不直接刷新目录。
- **合理推断**：目录快照和客户端绑定是为了避免配置刷新、认证切换与并发工具调用之间的错配。
- **合理推断**：BM25 搜索与延迟目录主要目标是降低工具 schema 对上下文的长期占用。
- **无法确认**：正式发行版中 model capability、feature 和远端配置的实际组合；这些决定工具最终是直接、延迟、Code Mode 还是隐藏。
- **无法确认**：第三方 Server 的分页行为、注解可信度、返回内容结构和是否支持协议级取消。

## 设计取舍

Codex 用不可变目录和精确客户端换取更强的调用一致性。代价是目录刷新、连接替换和工具准备之间需要更多协调；收益是模型看到某个工具后，执行不会因为后台刷新而无提示地落到另一份配置或另一个账号。

分页上限让巨型目录可控，但也会让超过 2,048 个工具的普通 Server 直接发现失败。Codex Apps 获得更高上限，是因为它是受信任的内置连接，而不是普通外部 Server 自动获得的特权。

延迟工具搜索节省上下文，但引入一次搜索往返，并要求模型正确描述能力。直接暴露更直接，但工具多时 schema 会长期占预算。Codex 的选择是把这两条路径做成明确的运行时暴露面，而不是只用一个布尔值隐藏工具。

审批同时参考配置和注解，比完全信任注解安全，也比每次一律询问更可用。将“批准当前会话”和“写入配置”做成不同结果，控制了持久授权的范围；把插件与 connector 纳入授权 key，则避免跨来源复用批准。

## 证据分级

### 已证实

- Server 配置、插件与扩展投影，以及每 Server 的连接和目录生命周期。
- 初始化握手、分页发现、目录缓存和会话过期重初始化。
- 启停过滤、UI 可见性、Apps 策略、名称规范化、schema 压缩与 namespace 封装。
- 直接、延迟搜索、Code Mode 和隐藏四类暴露边界。
- `tool_search` 的来源说明、BM25 搜索与可加载工具结果。
- 目录快照绑定的调用、审批模式、注解矩阵、审批记忆和 config 更新。
- 参数解析、协议调用、认证结果、内容转换、图片/音频能力降级与输出截断。
- 普通 Server 的 `tools/list_changed` 只记录日志。

### 合理推断

- 目录快照、客户端绑定和权限 profile 的组合是为刷新竞态与授权一致性服务。
- 分页上限和 schema 压缩是为了让不可信或失真的 Server 输出不会无限扩张客户端内存与模型上下文。
- 延迟搜索与 Code Mode 的共同目标是缩小常驻工具面，同时保留发现能力。

### 无法确认

- 构建期 feature、模型能力标记和远端配置在正式发行版中的真实组合。
- 具体第三方 Server 是否遵守可见性、注解、分页和错误语义。
- core 取消执行后，底层 RMCP 是否总会向 Server 发出协议级取消通知。
